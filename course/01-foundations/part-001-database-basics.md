# Part 001: Database คืออะไร, RDBMS, ทำไมต้อง PostgreSQL

> หลักสูตร PostgreSQL ฉบับสมบูรณ์ | ระดับพื้นฐาน | Part 001

ยินดีต้อนรับสู่หลักสูตร PostgreSQL ฉบับสมบูรณ์ครับ/ค่ะ นี่คือบทแรกของการเดินทางที่จะพาคุณจากศูนย์ไปสู่ระดับ world-class expert ในการใช้งาน PostgreSQL ซึ่งเป็นหนึ่งใน relational database ที่ทรงพลังและได้รับความนิยมสูงที่สุดในโลก ไม่ว่าคุณจะไม่เคยแตะฐานข้อมูลมาก่อนเลย หรือเคยใช้ฐานข้อมูลอื่นมาบ้างแล้วอยากมาทำความรู้จัก PostgreSQL อย่างจริงจัง บทนี้จะปูพื้นฐานความคิดที่จำเป็นทั้งหมดให้กับคุณก่อนที่เราจะเริ่มลงมือเขียนคำสั่งจริงในบทถัดไป

บทนี้จะไม่มีการเขียนโค้ด SQL จริงจัง เพราะเป้าหมายคือการสร้าง "แผนที่ความคิด" (mental model) ที่ถูกต้องเกี่ยวกับฐานข้อมูลก่อน เมื่อคุณเข้าใจว่าทำไมฐานข้อมูลถึงมีอยู่ ทำไมต้องมีกฎเกณฑ์ต่าง ๆ และทำไม PostgreSQL ถึงพิเศษ การเรียนรู้คำสั่ง SQL ในบทถัดไปจะง่ายขึ้นมาก เพราะคุณจะเข้าใจ "เหตุผล" เบื้องหลังทุกคำสั่งที่เขียน ไม่ใช่แค่จำรูปแบบไปเฉย ๆ

## เป้าหมายการเรียนรู้ (Learning Objectives)

เมื่อเรียนจบบทนี้ คุณจะสามารถ:

- อธิบายได้ว่า database คืออะไร และแก้ปัญหาอะไรที่การเก็บข้อมูลด้วยไฟล์ธรรมดาหรือ Excel ทำไม่ได้
- แยกแยะความแตกต่างระหว่างฐานข้อมูลประเภท Relational, NoSQL และ NewSQL พร้อมบอกข้อดีข้อเสียของแต่ละแบบ
- อธิบายแนวคิดพื้นฐานของ RDBMS ได้แก่ table, row, column และความสัมพันธ์ระหว่างตาราง
- อธิบายหลักการ ACID พร้อมยกตัวอย่างสถานการณ์จริงที่แสดงให้เห็นความสำคัญของแต่ละหลักการ
- เข้าใจว่า SQL คืออะไร มีมาตรฐานอย่างไร และแบ่งเป็นประเภทคำสั่งอะไรบ้าง (DDL, DML, DQL, DCL, TCL)
- เล่าประวัติความเป็นมาของ PostgreSQL ตั้งแต่ยุค Ingres/Postgres ที่ Berkeley จนถึงปัจจุบัน
- เปรียบเทียบจุดเด่นจุดด้อยของ PostgreSQL กับฐานข้อมูลอื่น ๆ ที่นิยมใช้ในอุตสาหกรรม
- เข้าใจภาพรวมสถาปัตยกรรมของ PostgreSQL แบบคร่าว ๆ ก่อนเจาะลึกในบทถัดไป
- รู้ว่าองค์กรระดับโลกใช้ PostgreSQL ในสถานการณ์แบบไหนบ้าง
- มองเห็นภาพรวมทั้งหลักสูตรว่าจะได้เรียนอะไรบ้างตั้งแต่ต้นจนจบ

## Step 1: Database คืออะไร

### นิยามแบบเข้าใจง่าย

**Database** (ฐานข้อมูล) คือ ระบบที่ถูกออกแบบมาเพื่อ **เก็บ จัดระเบียบ และจัดการข้อมูล** อย่างมีโครงสร้าง เพื่อให้สามารถเข้าถึง แก้ไข ค้นหา และวิเคราะห์ข้อมูลได้อย่างมีประสิทธิภาพ ปลอดภัย และเชื่อถือได้ ไม่ว่าข้อมูลนั้นจะมีผู้ใช้งานคนเดียวหรือพร้อมกันนับล้านคนก็ตาม

ลองนึกภาพร้านสะดวกซื้อที่มีสินค้าหลายพันรายการ ถ้าไม่มีระบบจัดการสต๊อกที่ดี พนักงานคงต้องเดินหาสินค้าทีละชั้นวาง จดบันทึกด้วยมือ และเสี่ยงต่อความผิดพลาดมหาศาล — database ก็เปรียบเสมือน "ระบบหลังบ้าน" ที่ทำให้ทุกอย่างเป็นระเบียบ ค้นหาได้ทันที และอัปเดตได้อย่างแม่นยำ

### ปัญหาที่เกิดขึ้นเมื่อเก็บข้อมูลด้วยไฟล์ธรรมดา หรือ Excel

หลายคนเริ่มต้นเก็บข้อมูลด้วย Excel, Google Sheets หรือไฟล์ text/CSV ธรรมดา ซึ่งใช้งานได้ดีในช่วงแรกที่ข้อมูลยังมีขนาดเล็กและมีผู้ใช้เพียงคนเดียว แต่เมื่อข้อมูลเติบโตขึ้น หรือมีคนใช้งานพร้อมกันหลายคน ปัญหาต่อไปนี้จะเริ่มปรากฏให้เห็นอย่างชัดเจน:

**1. ข้อมูลซ้ำซ้อน (Data Redundancy)**

สมมติร้านค้าออนไลน์เก็บข้อมูลคำสั่งซื้อใน Excel โดยแต่ละแถวมีชื่อลูกค้า ที่อยู่ เบอร์โทร และรายการสินค้า เมื่อลูกค้าคนเดิมสั่งซื้อครั้งที่สอง ข้อมูลชื่อ-ที่อยู่-เบอร์โทรจะถูกพิมพ์ซ้ำอีกครั้ง หากลูกค้าย้ายที่อยู่ พนักงานต้องไล่แก้ทุกแถวที่มีชื่อลูกค้าคนนั้น ถ้าลืมแก้แม้แต่แถวเดียว ข้อมูลก็จะไม่ตรงกัน (inconsistent)

**2. ไม่มีการควบคุมการเข้าถึงพร้อมกัน (Concurrency Control)**

เมื่อพนักงานสองคนเปิดไฟล์ Excel เดียวกันพร้อมกันและแก้ไขข้อมูลแถวเดียวกัน คนที่บันทึกทีหลังมักจะเขียนทับข้อมูลของคนแรกโดยไม่รู้ตัว ทำให้ข้อมูลหายไปโดยไม่มีการแจ้งเตือนใด ๆ

**3. ไม่มีการตรวจสอบความถูกต้องของข้อมูล (Data Validation / Integrity)**

ในไฟล์ Excel ไม่มีอะไรบังคับว่าช่อง "อายุ" ต้องเป็นตัวเลข หรือช่อง "อีเมล" ต้องมีรูปแบบที่ถูกต้อง พนักงานอาจพิมพ์ "สามสิบ" แทน "30" หรือปล่อยช่องสำคัญว่างไว้ ระบบก็ไม่ทักท้วงอะไร

**4. จัดการข้อมูลขนาดใหญ่ได้ยาก**

Excel มีขีดจำกัดจำนวนแถวและประสิทธิภาพจะตกลงอย่างเห็นได้ชัดเมื่อข้อมูลมีหลักแสนหรือหลักล้านแถว การค้นหาหรือคำนวณสรุปผล (เช่น ยอดขายรวมของเดือนที่แล้ว) จะช้าลงเรื่อย ๆ

**5. ไม่มีระบบสำรองข้อมูลและกู้คืนที่น่าเชื่อถือ**

หากไฟล์เสียหาย ถูกลบโดยไม่ตั้งใจ หรือเครื่องคอมพิวเตอร์พัง ข้อมูลทั้งหมดอาจหายไปถาวร โดยไม่มีกลไกป้องกันที่เป็นระบบ

**6. ความปลอดภัยต่ำ**

ไฟล์ Excel ทั่วไปควบคุมสิทธิ์การเข้าถึงได้อย่างจำกัดมาก เช่น ไม่สามารถกำหนดได้ว่า "พนักงานฝ่ายขายดูได้เฉพาะข้อมูลลูกค้า แต่แก้ไขราคาสินค้าไม่ได้"

### Database แก้ปัญหาเหล่านี้อย่างไร

Database ที่ออกแบบมาอย่างดี (โดยเฉพาะ RDBMS ซึ่งเราจะพูดถึงใน Step ถัดไป) จะช่วยแก้ปัญหาทั้งหมดข้างต้นด้วยกลไกดังนี้:

| ปัญหาจากไฟล์ธรรมดา | วิธีที่ Database แก้ไข |
|---|---|
| ข้อมูลซ้ำซ้อน | ออกแบบโครงสร้างข้อมูลให้เก็บแต่ละอย่างเพียงครั้งเดียว (normalization) แล้วเชื่อมโยงกันด้วยความสัมพันธ์ |
| แก้ไขพร้อมกันแล้วข้อมูลหาย | มีระบบ concurrency control และ transaction ที่รับประกันความถูกต้อง |
| ไม่ตรวจสอบความถูกต้อง | กำหนด data type, constraint และกฎทางธุรกิจได้ในระดับฐานข้อมูล |
| ช้าเมื่อข้อมูลใหญ่ | มี index และ query optimizer ที่ค้นหาข้อมูลได้รวดเร็วแม้ข้อมูลนับล้านแถว |
| ไม่มีการสำรองข้อมูล | มีระบบ backup, replication และ point-in-time recovery |
| ความปลอดภัยต่ำ | มีระบบ authentication, authorization และการเข้ารหัสข้อมูล |

กล่าวโดยสรุป database ไม่ใช่แค่ "ที่เก็บข้อมูล" แต่เป็น **ระบบที่รับประกันว่าข้อมูลจะถูกต้อง ปลอดภัย เข้าถึงได้เร็ว และใช้งานได้พร้อมกันหลายคนโดยไม่ชนกัน** — นี่คือเหตุผลว่าทำไมแทบทุกระบบซอฟต์แวร์ในโลก ตั้งแต่แอปธนาคาร ระบบจองตั๋วเครื่องบิน ไปจนถึงโซเชียลมีเดีย ล้วนมี database เป็นหัวใจสำคัญอยู่เบื้องหลัง

## Step 2: ประเภทของฐานข้อมูล — Relational vs NoSQL vs NewSQL

เมื่อเข้าใจแล้วว่า database มีไว้ทำอะไร ขั้นต่อไปคือทำความเข้าใจว่าฐานข้อมูลไม่ได้มีแบบเดียว แต่แบ่งออกเป็นหลายตระกูลตามวิธีการจัดเก็บและจัดการข้อมูล

### 2.1 Relational Database (RDBMS)

เก็บข้อมูลในรูปแบบ **ตาราง (table)** ที่มีแถว (row) และคอลัมน์ (column) ชัดเจน แต่ละตารางมี schema (โครงสร้าง) ที่กำหนดไว้ล่วงหน้าว่าแต่ละคอลัมน์เก็บข้อมูลประเภทใด และตารางต่าง ๆ เชื่อมโยงกันได้ด้วยความสัมพันธ์ (relationship) ตัวอย่างที่รู้จักกันดี ได้แก่ **PostgreSQL, MySQL, Oracle Database, Microsoft SQL Server, SQLite**

**ข้อดี**
- ข้อมูลมีโครงสร้างชัดเจน ตรวจสอบความถูกต้องได้ง่าย
- รองรับหลักการ ACID อย่างเข้มงวด เหมาะกับงานที่ต้องการความถูกต้องสูง เช่น ระบบการเงิน
- ใช้ SQL ซึ่งเป็นภาษามาตรฐานที่ได้รับการยอมรับอย่างกว้างขวาง มีระบบนิเวศเครื่องมือรองรับมหาศาล
- เหมาะกับข้อมูลที่มีความสัมพันธ์ซับซ้อน (เช่น ลูกค้า-คำสั่งซื้อ-สินค้า)

**ข้อเสีย**
- การปรับเปลี่ยนโครงสร้าง (schema) เมื่อข้อมูลเติบโตซับซ้อนขึ้นอาจต้องวางแผนล่วงหน้า
- การขยายระบบแนวนอน (horizontal scaling) แบบเดิมทำได้ยากกว่า NoSQL บางประเภท (แม้ปัจจุบันจะมีเทคนิคแก้ไขมากมาย)

### 2.2 NoSQL Database

"NoSQL" ย่อมาจาก "Not Only SQL" เป็นกลุ่มฐานข้อมูลที่ออกแบบมาให้ยืดหยุ่นกว่ารูปแบบตาราง แบ่งย่อยได้อีกหลายแบบ:

- **Document Database** เช่น MongoDB, Couchbase — เก็บข้อมูลเป็นเอกสาร (มักเป็น JSON) แต่ละเอกสารมีโครงสร้างยืดหยุ่น ไม่ต้องเหมือนกันทุกตัว
- **Key-Value Store** เช่น Redis, DynamoDB — เก็บข้อมูลเป็นคู่ key-value เรียบง่าย รวดเร็วมาก เหมาะกับ caching
- **Column-Family Store** เช่น Cassandra, HBase — เหมาะกับข้อมูลขนาดใหญ่มากที่ต้องเขียนเร็วและกระจายในหลายเครื่อง
- **Graph Database** เช่น Neo4j — เหมาะกับข้อมูลที่ความสัมพันธ์ซับซ้อนมาก เช่น เครือข่ายสังคม

**ข้อดี**
- ยืดหยุ่นเรื่อง schema เหมาะกับข้อมูลที่โครงสร้างเปลี่ยนแปลงบ่อยหรือไม่แน่นอน
- หลายตัวออกแบบมาให้ขยายระบบแนวนอน (scale out) ได้ง่ายตั้งแต่ต้น
- บางประเภท (เช่น key-value) มีความเร็วสูงมากสำหรับงานเฉพาะทาง

**ข้อเสีย**
- หลายตัวยอมผ่อนปรนหลักการ ACID บางส่วน เพื่อแลกกับความเร็วและการขยายระบบ (ตาม CAP theorem)
- การจัดการความสัมพันธ์ระหว่างข้อมูลที่ซับซ้อนทำได้ยากหรือไม่มีประสิทธิภาพเท่า RDBMS
- ระบบนิเวศเครื่องมือและมาตรฐานภาษา query หลากหลายและไม่เป็นหนึ่งเดียวเท่า SQL

### 2.3 NewSQL Database

เป็นแนวคิดที่พยายามผสมข้อดีสองฝั่งเข้าด้วยกัน คือรักษาความถูกต้องแบบ ACID และใช้ SQL เหมือน RDBMS ดั้งเดิม แต่ออกแบบสถาปัตยกรรมภายในให้ขยายระบบแนวนอนได้ดีแบบ NoSQL ตัวอย่างเช่น Google Spanner, CockroachDB, YugabyteDB

**ข้อดี**
- ได้ความถูกต้องแบบ ACID พร้อมความสามารถในการขยายระบบขนาดใหญ่
- ใช้ SQL ที่คุ้นเคย ลดต้นทุนการเรียนรู้

**ข้อเสีย**
- เทคโนโลยียังค่อนข้างใหม่เมื่อเทียบกับ RDBMS ดั้งเดิม ชุมชนและเครื่องมือสนับสนุนยังเล็กกว่า
- สถาปัตยกรรมภายในซับซ้อน อาจต้องการความเชี่ยวชาญเฉพาะทางในการดูแลระบบ

### สรุปเปรียบเทียบ

| ประเภท | จุดเด่น | เหมาะกับงาน |
|---|---|---|
| Relational (RDBMS) | โครงสร้างชัดเจน, ACID, SQL มาตรฐาน | ระบบธุรกิจทั่วไป, การเงิน, ERP, ข้อมูลที่มีความสัมพันธ์ซับซ้อน |
| NoSQL (Document) | schema ยืดหยุ่น | ข้อมูลที่โครงสร้างเปลี่ยนบ่อย, content management |
| NoSQL (Key-Value) | เร็วมาก | caching, session store |
| NoSQL (Graph) | จัดการความสัมพันธ์เชิงกราฟ | โซเชียลเน็ตเวิร์ก, recommendation engine |
| NewSQL | ACID + scale ได้ดี | ระบบขนาดใหญ่ระดับโลกที่ต้องการทั้งความถูกต้องและการขยายตัว |

**สิ่งสำคัญที่ต้องเข้าใจ**: ไม่มีฐานข้อมูลประเภทไหนที่ "ดีที่สุด" ในทุกสถานการณ์ การเลือกใช้ขึ้นอยู่กับลักษณะข้อมูลและความต้องการของระบบ แต่สำหรับงานส่วนใหญ่ในโลกธุรกิจที่ต้องการความถูกต้องของข้อมูลสูงและมีความสัมพันธ์ระหว่างข้อมูลชัดเจน **RDBMS ยังคงเป็นตัวเลือกอันดับต้น ๆ** และ PostgreSQL ก็เป็นหนึ่งใน RDBMS ที่ครบเครื่องที่สุดในปัจจุบัน (และยังรองรับการทำงานแบบ NoSQL บางส่วนได้ด้วย ซึ่งเราจะได้เห็นในบทหลัง ๆ)

## Step 3: RDBMS คืออะไร — ตาราง แถว คอลัมน์ และความสัมพันธ์

**RDBMS** ย่อมาจาก **Relational Database Management System** คือซอฟต์แวร์ที่ใช้จัดการฐานข้อมูลเชิงสัมพันธ์ (relational database) — PostgreSQL, MySQL, Oracle, SQL Server ล้วนเป็น RDBMS ทั้งสิ้น

### แนวคิดพื้นฐาน: Table, Row, Column

ลองจินตนาการว่าคุณกำลังจดบันทึกรายชื่อนักเรียนในสมุดที่ตีตารางไว้:

```
+----+---------------+-----+---------------------+
| id | ชื่อ           | อายุ | อีเมล                |
+----+---------------+-----+---------------------+
| 1  | สมชาย ใจดี     | 20  | somchai@email.com   |
| 2  | สมหญิง รักเรียน | 22  | somying@email.com   |
| 3  | วิชัย มานะ      | 21  | wichai@email.com    |
+----+---------------+-----+---------------------+
```

นี่คือแนวคิดพื้นฐานที่สุดของ RDBMS:

- **Table (ตาราง)** คือโครงสร้างหลักที่ใช้เก็บข้อมูลเรื่องใดเรื่องหนึ่ง เช่น ตาราง `students` เก็บข้อมูลนักเรียน ตาราง `courses` เก็บข้อมูลรายวิชา
- **Row (แถว)** หรือเรียกอีกชื่อว่า **record** คือข้อมูลหนึ่งชุดที่สมบูรณ์ในตาราง เช่น ข้อมูลของนักเรียนหนึ่งคน
- **Column (คอลัมน์)** หรือเรียกอีกชื่อว่า **field** คือคุณสมบัติแต่ละอย่างของข้อมูล เช่น ชื่อ, อายุ, อีเมล แต่ละคอลัมน์จะถูกกำหนด **data type** ไว้ล่วงหน้า เช่น ตัวเลข, ข้อความ, วันที่ เพื่อรับประกันว่าข้อมูลที่บันทึกจะถูกต้องตามรูปแบบเสมอ

### Primary Key: กุญแจสำคัญของแต่ละแถว

สังเกตคอลัมน์ `id` ในตารางด้านบน นี่คือสิ่งที่เรียกว่า **primary key** — ค่าที่ไม่ซ้ำกันเลยในแต่ละแถว ใช้เป็น "ตัวระบุตัวตน" ที่ไม่กำกวมของแต่ละ record เปรียบได้กับเลขบัตรประชาชนของคน แม้ว่าจะมีคนชื่อ "สมชาย" ซ้ำกันหลายคนในตาราง แต่ `id` จะไม่มีวันซ้ำ ทำให้ระบบสามารถระบุแถวใดแถวหนึ่งได้อย่างแม่นยำ 100%

### ความสัมพันธ์ระหว่างตาราง (Relationships)

จุดเด่นที่แท้จริงของ RDBMS คือความสามารถในการ**เชื่อมโยงตารางหลายตารางเข้าด้วยกัน** แทนที่จะยัดข้อมูลทั้งหมดไว้ในตารางเดียวจนซ้ำซ้อน

ตัวอย่างเช่น ระบบร้านค้าออนไลน์อาจมีตาราง:

```
ตาราง customers (ลูกค้า)          ตาราง orders (คำสั่งซื้อ)
+----+----------+              +----+-------------+------------+
| id | ชื่อ      |              | id | customer_id | total      |
+----+----------+              +----+-------------+------------+
| 1  | สมชาย     |              | 101| 1           | 1,500 บาท  |
| 2  | สมหญิง    |              | 102| 1           | 2,300 บาท  |
+----+----------+              | 103| 2           | 800 บาท    |
                                +----+-------------+------------+
```

คอลัมน์ `customer_id` ในตาราง `orders` คือ **foreign key** ที่ชี้กลับไปหา `id` ในตาราง `customers` — นี่คือกลไกที่ทำให้เราไม่ต้องพิมพ์ชื่อ-ที่อยู่-เบอร์โทรของลูกค้าซ้ำทุกครั้งที่มีคำสั่งซื้อใหม่ เราเก็บข้อมูลลูกค้าไว้ที่เดียว แล้ว "อ้างอิง" กลับไปหาด้วย id เท่านั้น

ความสัมพันธ์ระหว่างตารางมีหลายแบบ:

- **One-to-Many (หนึ่งต่อกลาย)**: ลูกค้าหนึ่งคนมีได้หลายคำสั่งซื้อ (พบบ่อยที่สุด)
- **Many-to-Many (กลายต่อกลาย)**: นักเรียนหนึ่งคนลงทะเบียนได้หลายวิชา และแต่ละวิชาก็มีนักเรียนหลายคน (ต้องใช้ตารางกลางเชื่อม)
- **One-to-One (หนึ่งต่อหนึ่ง)**: พนักงานหนึ่งคนมีข้อมูลบัตรพนักงานได้หนึ่งใบ

การออกแบบตารางและความสัมพันธ์ให้ถูกต้องนี้เรียกว่า **database design / normalization** ซึ่งเราจะเรียนรู้อย่างละเอียดในบทถัดไปของหลักสูตร แต่ตอนนี้ขอให้คุณจำแนวคิดหลักไว้ก่อนว่า: **RDBMS ทำงานโดยแยกข้อมูลออกเป็นตารางย่อยที่มีความรับผิดชอบชัดเจน แล้วเชื่อมโยงกันด้วย key** — นี่คือรากฐานของทุกอย่างที่เราจะเรียนต่อจากนี้

## Step 4: หลักการ ACID

หนึ่งในเหตุผลสำคัญที่สุดที่ RDBMS อย่าง PostgreSQL ได้รับความไว้วางใจให้ใช้งานกับข้อมูลสำคัญ (เช่น ธุรกรรมทางการเงิน) คือการรับประกัน **ACID** ซึ่งเป็นชุดคุณสมบัติสี่ข้อที่ทำให้มั่นใจได้ว่าข้อมูลจะถูกต้องเสมอ แม้ในสถานการณ์ที่ระบบขัดข้องหรือมีผู้ใช้หลายคนทำงานพร้อมกัน

ให้เราใช้ตัวอย่างที่เข้าใจง่ายที่สุด: **การโอนเงินระหว่างบัญชีธนาคาร** สมมติสมชายต้องการโอนเงิน 1,000 บาท ให้สมหญิง การทำธุรกรรมนี้จริง ๆ แล้วประกอบด้วยสองขั้นตอน:

1. หักเงิน 1,000 บาท จากบัญชีสมชาย
2. เพิ่มเงิน 1,000 บาท เข้าบัญชีสมหญิง

### A — Atomicity (ความเป็นอะตอม)

**Atomicity** หมายความว่า การทำงานทั้งชุด (เรียกว่า **transaction**) จะต้องสำเร็จ**ทั้งหมด**หรือไม่สำเร็จเลย ไม่มีสถานะครึ่ง ๆ กลาง ๆ

ในตัวอย่างการโอนเงิน สมมติระบบหักเงินจากบัญชีสมชายสำเร็จแล้ว (ขั้นตอนที่ 1) แต่เกิดไฟดับหรือระบบล่มก่อนที่จะเพิ่มเงินเข้าบัญชีสมหญิง (ขั้นตอนที่ 2) — หากไม่มี atomicity เงิน 1,000 บาทจะ "หายไป" จากระบบเฉย ๆ สมชายเสียเงินแต่สมหญิงไม่ได้รับ

ด้วยหลักการ Atomicity, PostgreSQL จะมองทั้งสองขั้นตอนนี้เป็น**หน่วยเดียว**กัน หากขั้นตอนใดขั้นตอนหนึ่งล้มเหลว ระบบจะ **ยกเลิก (rollback)** ทุกอย่างที่ทำไปแล้วในหน่วยนั้น ทำให้บัญชีสมชายกลับมามีเงินเท่าเดิม เสมือนไม่มีอะไรเกิดขึ้นเลย

### C — Consistency (ความสอดคล้อง)

**Consistency** หมายความว่า ข้อมูลจะต้องอยู่ใน**สถานะที่ถูกต้องตามกฎ**เสมอ ทั้งก่อนและหลังทำ transaction — กฎในที่นี้อาจเป็นกฎที่ฐานข้อมูลกำหนด (เช่น ยอดเงินในบัญชีห้ามติดลบ) หรือกฎทางธุรกิจ

ในตัวอย่างการโอนเงิน สมมติมีกฎว่า "ยอดเงินรวมทั้งระบบธนาคารต้องคงที่เสมอ ไม่มีการสร้างเงินขึ้นมาลอย ๆ หรือหายไปลอย ๆ" — ก่อนโอน ยอดรวมของสมชาย + สมหญิง เท่ากับ X บาท หลังโอนเสร็จ ยอดรวมก็ยังต้องเท่ากับ X บาทเหมือนเดิม เพียงแค่สัดส่วนเปลี่ยนไป หาก consistency ถูกละเมิด (เช่น มีบั๊กทำให้เงินเพิ่มขึ้นมาเองระหว่างทาง) นั่นคือความผิดพลาดร้ายแรงที่ฐานข้อมูลต้องป้องกันไม่ให้เกิดขึ้น

### I — Isolation (ความเป็นเอกเทศ)

**Isolation** หมายความว่า เมื่อมีหลาย transaction ทำงาน**พร้อมกัน** แต่ละ transaction จะต้องไม่เห็นผลกระทบที่ยังไม่เสร็จสมบูรณ์ของ transaction อื่น

ลองนึกภาพว่าขณะที่สมชายกำลังโอนเงินให้สมหญิง มีอีกธุรกรรมหนึ่งกำลังตรวจสอบยอดเงินคงเหลือในบัญชีสมชายพร้อมกันพอดี (เช่น ระบบแสดงยอดเงินในแอปมือถือ) หากไม่มี isolation ระบบตรวจสอบอาจไปอ่านเจอสถานะ "ครึ่ง ๆ กลาง ๆ" เช่น เห็นว่าเงินถูกหักออกจากสมชายแล้ว แต่ยังไม่ทันเห็นว่าเงินเข้าสมหญิงหรือยัง ทำให้ยอดรวมที่แสดงผิดเพี้ยนไปชั่วขณะ

Isolation ทำให้แต่ละ transaction ทำงานราวกับว่าตัวเองเป็น transaction เดียวในระบบ แม้จริง ๆ แล้วจะมีอีกหลายสิบหลายร้อย transaction กำลังทำงานพร้อมกันอยู่ก็ตาม (ในบทหลัง ๆ เราจะเรียนรู้ระดับของ isolation ที่ปรับแต่งได้ในรายละเอียด)

### D — Durability (ความคงทน)

**Durability** หมายความว่า เมื่อ transaction ยืนยันเสร็จสมบูรณ์แล้ว (commit) ข้อมูลนั้นจะ**ถูกบันทึกอย่างถาวร** แม้ระบบจะเกิดไฟดับ เครื่องดับ หรือขัดข้องทันทีหลังจากนั้นก็ตาม

หลังจากสมหญิงได้รับเงิน 1,000 บาทเข้าบัญชีและระบบแจ้งว่า "โอนสำเร็จ" แล้ว หากทันใดนั้นเซิร์ฟเวอร์ธนาคารเกิดไฟดับ เมื่อเปิดเครื่องขึ้นมาใหม่ เงิน 1,000 บาทนั้นจะต้องยังอยู่ในบัญชีสมหญิงเสมอ ไม่มีทางหายไปได้ — นี่คือสิ่งที่ทำให้เราไว้วางใจระบบธนาคารได้ PostgreSQL ทำสิ่งนี้ได้ด้วยกลไกที่เรียกว่า **WAL (Write-Ahead Logging)** ซึ่งเราจะเจาะลึกในบทที่ว่าด้วยสถาปัตยกรรมภายใน

### สรุป ACID ด้วยตารางเดียว

| หลักการ | ความหมาย | ถ้าไม่มี จะเกิดอะไรขึ้น (ตัวอย่างโอนเงิน) |
|---|---|---|
| **A**tomicity | ทำทั้งหมดหรือไม่ทำเลย | เงินหักจากคนโอนแต่ไม่เข้าคนรับ เงินหายไปเฉย ๆ |
| **C**onsistency | ข้อมูลถูกต้องตามกฎเสมอ | ยอดเงินรวมในระบบผิดเพี้ยนไปจากความเป็นจริง |
| **I**solation | ธุรกรรมพร้อมกันไม่รบกวนกัน | เห็นยอดเงินผิด ๆ ระหว่างที่ธุรกรรมอื่นยังทำไม่เสร็จ |
| **D**urability | บันทึกแล้วต้องอยู่ถาวร | ไฟดับแล้วเงินที่โอนสำเร็จไปแล้วหายไป |

PostgreSQL คือหนึ่งใน RDBMS ที่ยึดมั่นในหลักการ ACID อย่างเคร่งครัดที่สุด นี่คือเหตุผลสำคัญที่องค์กรจำนวนมากที่ต้องการความถูกต้องของข้อมูลระดับสูงสุด (การเงิน, การแพทย์, ระบบภาครัฐ) เลือกใช้ PostgreSQL

## Step 5: SQL คืออะไร

### นิยามของ SQL

**SQL** ย่อมาจาก **Structured Query Language** คือภาษามาตรฐานที่ใช้สำหรับสื่อสารกับฐานข้อมูลเชิงสัมพันธ์ (RDBMS) ไม่ว่าจะเป็นการสร้างโครงสร้างข้อมูล เพิ่ม แก้ไข ลบ หรือค้นหาข้อมูล เราใช้ SQL ในการบอกฐานข้อมูลว่า "ต้องการอะไร" ("อยากได้ข้อมูลลูกค้าที่อยู่กรุงเทพและสั่งซื้อมากกว่า 5 ครั้งในเดือนที่แล้ว") มากกว่าจะบอกว่า "ต้องทำอย่างไรทีละขั้นตอน" — นี่ทำให้ SQL เป็นภาษาประเภท **declarative** (บอกผลลัพธ์ที่ต้องการ ไม่ใช่บอกขั้นตอน)

### มาตรฐาน SQL

SQL ไม่ใช่ภาษาที่ผูกติดกับฐานข้อมูลใดฐานข้อมูลหนึ่ง แต่เป็น**มาตรฐานสากล**ที่ดูแลโดยองค์กร ISO/IEC (International Organization for Standardization) และ ANSI (American National Standards Institute) มาตรฐานนี้มีการปรับปรุงเป็นระยะ (เช่น SQL-92, SQL:1999, SQL:2003, SQL:2016, SQL:2023) เพื่อเพิ่มความสามารถใหม่ ๆ เข้าไปเรื่อย ๆ

สิ่งสำคัญที่ต้องเข้าใจคือ RDBMS แต่ละตัว (PostgreSQL, MySQL, Oracle, SQL Server) จะ**ปฏิบัติตามมาตรฐาน SQL เป็นหลัก** แต่ก็มักจะมี "ส่วนขยาย" (extension) หรือฟีเจอร์พิเศษเฉพาะของตัวเองเพิ่มเติมด้วย ซึ่งเป็นเหตุผลว่าทำไมโค้ด SQL ที่เขียนสำหรับฐานข้อมูลหนึ่งอาจไม่สามารถนำไปรันบนอีกฐานข้อมูลหนึ่งได้ทันทีแบบ 100% — PostgreSQL ได้รับการยอมรับอย่างกว้างขวางว่าเป็นหนึ่งในฐานข้อมูลที่ **ปฏิบัติตามมาตรฐาน SQL ได้ครบถ้วนและถูกต้องที่สุด** ในบรรดา RDBMS ยอดนิยมทั้งหมด

### ประเภทของคำสั่ง SQL

คำสั่ง SQL แบ่งออกเป็นกลุ่มย่อยตามหน้าที่การทำงาน ซึ่งเราจะได้เรียนรู้ทีละกลุ่มอย่างละเอียดตลอดหลักสูตรนี้ แต่ในบทนี้ขอให้ทำความรู้จักภาพรวมไว้ก่อน:

**1. DDL — Data Definition Language (ภาษาสำหรับกำหนดโครงสร้างข้อมูล)**

ใช้สำหรับสร้าง แก้ไข หรือลบ "โครงสร้าง" ของฐานข้อมูล เช่น ตาราง, index, view คำสั่งสำคัญในกลุ่มนี้ได้แก่ `CREATE`, `ALTER`, `DROP`, `TRUNCATE`

> เปรียบเทียบ: เหมือนการสร้างและออกแบบตู้เอกสาร กำหนดว่าจะมีลิ้นชักกี่ช่อง แต่ละช่องเก็บอะไร

**2. DML — Data Manipulation Language (ภาษาสำหรับจัดการข้อมูล)**

ใช้สำหรับเพิ่ม แก้ไข หรือลบ "ข้อมูล" ภายในตารางที่มีอยู่แล้ว คำสั่งสำคัญได้แก่ `INSERT`, `UPDATE`, `DELETE`

> เปรียบเทียบ: เหมือนการใส่เอกสารเข้าลิ้นชัก แก้ไขเอกสารที่มีอยู่ หรือทิ้งเอกสารที่ไม่ต้องการแล้ว

**3. DQL — Data Query Language (ภาษาสำหรับค้นหาข้อมูล)**

ใช้สำหรับค้นหาและดึงข้อมูลออกมาดู คำสั่งหลักคือ `SELECT` ซึ่งเป็นคำสั่งที่คุณจะได้ใช้บ่อยที่สุดตลอดการทำงานกับฐานข้อมูล (บางตำราจะรวม DQL เข้าไปเป็นส่วนหนึ่งของ DML แต่ในหลักสูตรนี้เราจะแยกให้เห็นชัดเจนเพราะ `SELECT` มีความสำคัญและซับซ้อนมากพอที่จะแยกพูดถึงต่างหาก)

> เปรียบเทียบ: เหมือนการค้นหาเอกสารในตู้เก็บเอกสารตามเงื่อนไขที่ต้องการ

**4. DCL — Data Control Language (ภาษาสำหรับควบคุมสิทธิ์การเข้าถึง)**

ใช้สำหรับกำหนดว่าใครมีสิทธิ์ทำอะไรได้บ้างกับข้อมูล คำสั่งสำคัญได้แก่ `GRANT` (ให้สิทธิ์), `REVOKE` (ถอนสิทธิ์)

> เปรียบเทียบ: เหมือนการกำหนดว่าใครถือกุญแจตู้เอกสารได้บ้าง และแต่ละคนเปิดได้กี่ลิ้นชัก

**5. TCL — Transaction Control Language (ภาษาสำหรับควบคุม transaction)**

ใช้สำหรับจัดการ transaction ที่เราพูดถึงในเรื่อง ACID ก่อนหน้านี้ คำสั่งสำคัญได้แก่ `COMMIT` (ยืนยันการเปลี่ยนแปลง), `ROLLBACK` (ยกเลิกการเปลี่ยนแปลง), `SAVEPOINT` (จุดพักที่ยกเลิกกลับมาได้บางส่วน)

> เปรียบเทียบ: เหมือนการพูดว่า "ตกลง บันทึกการเปลี่ยนแปลงทั้งหมดนี้เลย" หรือ "ไม่เอาแล้ว ยกเลิกทุกอย่างที่เพิ่งทำไป กลับไปเป็นเหมือนเดิม"

### สรุปตาราง

| กลุ่มคำสั่ง | ชื่อเต็ม | ตัวอย่างคำสั่ง | หน้าที่ |
|---|---|---|---|
| DDL | Data Definition Language | `CREATE`, `ALTER`, `DROP` | กำหนด/แก้ไขโครงสร้าง |
| DML | Data Manipulation Language | `INSERT`, `UPDATE`, `DELETE` | จัดการข้อมูลในตาราง |
| DQL | Data Query Language | `SELECT` | ค้นหา/ดึงข้อมูล |
| DCL | Data Control Language | `GRANT`, `REVOKE` | ควบคุมสิทธิ์การเข้าถึง |
| TCL | Transaction Control Language | `COMMIT`, `ROLLBACK`, `SAVEPOINT` | ควบคุม transaction |

ไม่ต้องกังวลหากยังจำคำสั่งเหล่านี้ไม่ได้ในตอนนี้ — บทนี้เป็นเพียงการปูภาพรวมให้เห็นว่า SQL มีกลุ่มคำสั่งอะไรบ้าง ในบทถัดไปของหลักสูตรเราจะเริ่มลงมือใช้คำสั่งเหล่านี้จริง ๆ ทีละกลุ่มอย่างละเอียด

## Step 6: ประวัติของ PostgreSQL

การเข้าใจที่มาที่ไปของ PostgreSQL จะช่วยให้คุณเข้าใจว่าทำไมมันถึงมีปรัชญาการออกแบบที่เน้น "ความถูกต้องและความสามารถในการขยายตัว" มากกว่าฐานข้อมูลอื่น ๆ หลายตัว

### จุดเริ่มต้น: Ingres (ทศวรรษ 1970)

เรื่องราวเริ่มต้นที่มหาวิทยาลัย **University of California, Berkeley** โดยศาสตราจารย์ **Michael Stonebraker** (ผู้ซึ่งภายหลังได้รับรางวัล Turing Award อันทรงเกียรติในวงการวิทยาการคอมพิวเตอร์) ได้พัฒนาระบบฐานข้อมูลชื่อ **Ingres** ขึ้นในช่วงปี 1970s ซึ่งเป็นหนึ่งในโครงการฐานข้อมูลเชิงสัมพันธ์ยุคบุกเบิกของโลก

### กำเนิด Postgres (1986)

หลังจากทำงานกับ Ingres มาระยะหนึ่ง Stonebraker และทีมงานเริ่มมองเห็นข้อจำกัดของระบบฐานข้อมูลเชิงสัมพันธ์ในยุคนั้น จึงเริ่มโครงการใหม่ในปี **1986** ชื่อว่า **Postgres** (ย่อมาจาก "POST-ingres" หมายถึง "สิ่งที่มาหลัง Ingres") โดยมีเป้าหมายเพื่อแก้ปัญหาสำคัญสองประการที่ระบบยุคนั้นยังทำไม่ได้ดี:

1. รองรับ **data type ที่ซับซ้อน** มากกว่าตัวเลขและข้อความธรรมดา
2. รองรับแนวคิด **object-oriented** ผสมผสานเข้ากับโมเดลเชิงสัมพันธ์ ทำให้ Postgres ได้รับฉายาว่าเป็นฐานข้อมูลแบบ **"Object-Relational"** ซึ่งเป็นหนึ่งในจุดเด่นที่ยังคงอยู่มาจนถึงปัจจุบัน

### เปลี่ยนมาใช้ SQL: Postgres95 (1994–1995)

Postgres ดั้งเดิมใช้ภาษา query ของตัวเองชื่อ PostQuel ไม่ใช่ SQL ต่อมาในปี 1994 นักศึกษาปริญญาเอกสองคนคือ **Andrew Yu** และ **Jolly Chen** ได้เพิ่มตัวแปลภาษา SQL เข้าไปในระบบ และเปลี่ยนชื่อโครงการเป็น **Postgres95** พร้อมทั้งเผยแพร่เป็นซอฟต์แวร์โอเพนซอร์ส

### กำเนิดชื่อ PostgreSQL (1996)

ในปี **1996** โครงการถูกเปลี่ยนชื่ออีกครั้งเป็น **PostgreSQL** เพื่อสะท้อนให้เห็นถึงการรองรับมาตรฐาน SQL อย่างเต็มรูปแบบ และนี่คือชื่อที่ใช้มาจนถึงปัจจุบัน โครงการดำเนินต่อมาภายใต้การดูแลของชุมชนนักพัฒนาโอเพนซอร์สทั่วโลก (community-driven, ไม่ได้เป็นของบริษัทใดบริษัทหนึ่ง) โดยมีการออกเวอร์ชันใหม่อย่างต่อเนื่องสม่ำเสมอปีละครั้งมาจนถึงทุกวันนี้ พร้อมทั้งมีรอบการอัปเดตด้านความปลอดภัย (security patch) สำหรับแต่ละเวอร์ชันหลักเป็นระยะเวลาหลายปี

### ทำไมถึงเรียกว่า "the world's most advanced open source database"

วลีนี้เป็นสโลแกนที่ใช้ในเว็บไซต์ทางการของ PostgreSQL มายาวนาน และมีเหตุผลรองรับที่ชัดเจนหลายประการ:

- **ความสามารถทางเทคนิคที่ครบเครื่อง**: PostgreSQL ไม่ได้เป็นแค่ RDBMS ธรรมดา แต่รองรับ JSON/JSONB (ทำงานคล้าย document database ได้), full-text search, geospatial data (ผ่าน extension อย่าง PostGIS), custom data type, procedural language หลายภาษา และอีกมากมาย
- **ความสามารถในการขยาย (extensibility)**: ผู้ใช้สามารถสร้าง data type, function, operator, index type ของตัวเองขึ้นมาเสริมได้ ทำให้ระบบนิเวศ extension ของ PostgreSQL อุดมสมบูรณ์อย่างยิ่ง
- **ยึดมั่นในมาตรฐาน SQL และหลักการ ACID อย่างเคร่งครัด**: ไม่ยอมลดทอนความถูกต้องของข้อมูลเพื่อแลกกับความเร็ว
- **พัฒนาโดยชุมชนที่แข็งแกร่งและเป็นกลาง**: ไม่ผูกติดกับบริษัทใดบริษัทหนึ่ง (ต่างจากหลายผลิตภัณฑ์ที่แม้จะเป็นโอเพนซอร์สแต่ถูกควบคุมทิศทางโดยบริษัทเจ้าของ) ทำให้การพัฒนามีความต่อเนื่องและมุ่งเน้นคุณภาพทางวิศวกรรมระยะยาว
- **ใบอนุญาตแบบเสรีอย่างแท้จริง**: PostgreSQL ใช้ PostgreSQL License ซึ่งเป็น permissive license คล้าย MIT/BSD ใช้งานได้ฟรีทั้งในเชิงพาณิชย์และไม่ใช่เชิงพาณิชย์ โดยไม่มีข้อผูกมัดใด ๆ

กล่าวอีกนัยหนึ่งคือ PostgreSQL เดินทางมาไกลกว่า 40 ปีจากจุดเริ่มต้นในห้องทดลองของมหาวิทยาลัย ผ่านการพิสูจน์ตัวเองมานับครั้งไม่ถ้วนในระบบงานจริงระดับโลก จนกลายเป็นหนึ่งในฐานข้อมูลที่น่าเชื่อถือและทรงพลังที่สุดที่มีอยู่ในปัจจุบัน

## Step 7: จุดเด่นของ PostgreSQL เทียบกับฐานข้อมูลอื่น

เพื่อให้คุณเห็นภาพชัดเจนว่า PostgreSQL อยู่ตรงไหนในโลกของฐานข้อมูล เรามาเปรียบเทียบกับผู้เล่นหลักในตลาดกัน โดยเน้นการเปรียบเทียบเชิงคุณภาพอย่างตรงไปตรงมา ไม่มีการยกให้ฝ่ายใดฝ่ายหนึ่ง "ชนะ" ในทุกด้าน เพราะแต่ละระบบมีจุดแข็งและบริบทการใช้งานที่เหมาะสมต่างกัน

| หัวข้อเปรียบเทียบ | PostgreSQL | MySQL | SQL Server | Oracle Database | MongoDB |
|---|---|---|---|---|---|
| ประเภท | RDBMS (Object-Relational) | RDBMS | RDBMS | RDBMS | NoSQL (Document) |
| ใบอนุญาต | โอเพนซอร์ส (permissive) | โอเพนซอร์ส (GPL) + เวอร์ชันพาณิชย์ | เชิงพาณิชย์ (มีรุ่นฟรีจำกัด) | เชิงพาณิชย์ (ราคาสูง) | โอเพนซอร์ส/เชิงพาณิชย์ผสม |
| ความยึดมั่นต่อมาตรฐาน SQL | สูงมาก | ปานกลาง (มีความเบี่ยงเบนจากมาตรฐานบางจุด) | สูง | สูงมาก | ไม่ใช้ SQL แบบดั้งเดิม |
| Data type ที่รองรับ | หลากหลายมาก รวมถึง JSON/JSONB, array, geometric, custom type | พื้นฐานทั่วไป | หลากหลาย | หลากหลายมาก | เอกสาร JSON-like (BSON) |
| Extensibility | ยอดเยี่ยม (extension, custom type/function) | จำกัดกว่า | จำกัดกว่า | มี แต่ผูกกับระบบนิเวศ Oracle | จำกัด |
| การรองรับ concurrency | ยอดเยี่ยม (MVCC) | ดี | ดี | ยอดเยี่ยม | ดี (แบบ NoSQL) |
| เหมาะกับ query ซับซ้อน/analytics | ยอดเยี่ยม | ปานกลาง | ดี | ยอดเยี่ยม | ไม่เหมาะเท่า RDBMS |
| ต้นทุนการใช้งาน | ฟรี | ฟรี (ส่วนใหญ่) | มีค่าใช้จ่ายสูงในองค์กรใหญ่ | สูงมาก | ฟรี/มีค่าใช้จ่ายตามแผน |
| ชุมชนและระบบนิเวศ | แข็งแกร่งมาก เติบโตต่อเนื่อง | แข็งแกร่งมาก (โดยเฉพาะสาย web) | แข็งแกร่งในองค์กรที่ใช้ Microsoft stack | แข็งแกร่งในองค์กรขนาดใหญ่ดั้งเดิม | แข็งแกร่งในสาย modern app dev |

### อธิบายเพิ่มเติมแต่ละคู่เปรียบเทียบ

**PostgreSQL vs MySQL**

ทั้งคู่เป็นโอเพนซอร์สและได้รับความนิยมสูงมากในวงการเว็บ แต่ปรัชญาต่างกัน MySQL เดิมออกแบบมาเน้นความเรียบง่ายและความเร็วสำหรับงานอ่านเป็นหลัก (โดยเฉพาะในยุคแรกที่ยังไม่รองรับ transaction เต็มรูปแบบในทุก storage engine) ส่วน PostgreSQL เน้นความถูกต้องของข้อมูลและความสามารถขั้นสูงมาตั้งแต่ต้น ปัจจุบัน MySQL พัฒนาไปมากแล้ว แต่ PostgreSQL ยังคงได้เปรียบในเรื่องความสามารถขั้นสูง (advanced SQL features), การรองรับ data type ที่หลากหลาย และความยึดมั่นต่อมาตรฐาน SQL

**PostgreSQL vs SQL Server**

SQL Server เป็นผลิตภัณฑ์เชิงพาณิชย์ของ Microsoft ผูกกับระบบนิเวศ Windows/.NET อย่างแนบแน่น (แม้ปัจจุบันจะรองรับ Linux แล้วก็ตาม) มีเครื่องมือ GUI ที่ครบเครื่องและ support จากบริษัทโดยตรง แต่มีค่าใช้จ่ายด้าน license ที่สูงขึ้นตามขนาดการใช้งาน ขณะที่ PostgreSQL ให้ความสามารถใกล้เคียงหรือในหลายด้านเหนือกว่าโดยไม่มีค่าใช้จ่าย license เลย

**PostgreSQL vs Oracle Database**

Oracle เป็นฐานข้อมูลระดับองค์กรที่ครองตลาดองค์กรขนาดใหญ่มายาวนาน มีฟีเจอร์ enterprise ครบเครื่องและ support ระดับสูงมาก แต่ค่าใช้จ่ายด้าน license และ support สูงมากเช่นกัน ปัจจุบันหลายองค์กรเริ่มพิจารณา "ย้ายจาก Oracle มา PostgreSQL" (Oracle-to-PostgreSQL migration) เพื่อลดต้นทุน โดย PostgreSQL ในเวอร์ชันปัจจุบันมีความสามารถเพียงพอสำหรับงาน enterprise จำนวนมากแล้ว

**PostgreSQL vs MongoDB**

นี่คือการเปรียบเทียบระหว่างคนละตระกูล (RDBMS vs Document database) ไม่ใช่คู่แข่งโดยตรงเสียทีเดียว MongoDB เหมาะกับข้อมูลที่โครงสร้างไม่แน่นอนหรือเปลี่ยนแปลงบ่อย และมักเลือกใช้เมื่อไม่ต้องการความสัมพันธ์ซับซ้อนระหว่างข้อมูล ขณะที่ PostgreSQL เหมาะกับข้อมูลที่มีความสัมพันธ์ชัดเจนและต้องการความถูกต้องระดับ ACID สูง ที่น่าสนใจคือ PostgreSQL รองรับ JSONB ซึ่งทำให้สามารถเก็บและ query ข้อมูลแบบ document-style ได้ดีในระดับหนึ่งเช่นกัน ทำให้หลายทีมเลือกใช้ PostgreSQL เป็น "ฐานข้อมูลเดียวที่ตอบโจทย์ได้ทั้งสองแบบ" แทนที่จะต้องดูแลระบบสองระบบแยกกัน

### สรุปจุดเด่นของ PostgreSQL โดยรวม

1. **ฟรีและโอเพนซอร์สอย่างแท้จริง** ไม่มีข้อจำกัดด้านใบอนุญาตที่ซ่อนอยู่
2. **ยึดมั่นในมาตรฐาน SQL และ ACID อย่างเคร่งครัด** เหมาะกับงานที่ต้องการความถูกต้องสูง
3. **ความสามารถขั้นสูงครบเครื่อง** ทั้ง JSON, full-text search, geospatial, window function, CTE, และอื่น ๆ อีกมาก
4. **ขยายได้ (extensible)** ผ่านระบบ extension ที่หลากหลาย เช่น PostGIS (ข้อมูลภูมิสารสนเทศ), TimescaleDB (time-series), pgvector (AI/vector search)
5. **ชุมชนแข็งแกร่งและเป็นกลาง** ไม่ผูกกับบริษัทใดบริษัทหนึ่ง พัฒนาต่อเนื่องมาแล้วกว่า 25 ปีนับตั้งแต่เปลี่ยนชื่อเป็น PostgreSQL

## Step 8: สถาปัตยกรรมโดยรวมของ PostgreSQL (เกริ่นนำ)

ในบทนี้เราจะพูดถึงสถาปัตยกรรมของ PostgreSQL แบบ**คร่าว ๆ พอให้เห็นภาพรวม** เท่านั้น รายละเอียดเชิงลึก เช่น process model แบบเต็มรูปแบบ, memory architecture, WAL, MVCC และ storage layer จะมีบทเฉพาะที่เจาะลึกในภายหลังของหลักสูตร

### แบบจำลอง Client-Server

PostgreSQL ทำงานตามสถาปัตยกรรมแบบ **client-server** ซึ่งหมายความว่ามีสององค์ประกอบหลักที่ทำงานแยกจากกัน:

```
+------------------+                      +---------------------+
|                  |    ส่งคำสั่ง SQL       |                     |
|  Client          |  ------------------>  |  PostgreSQL Server  |
|  (psql, pgAdmin, |                      |  (postgres process)  |
|   แอปพลิเคชัน)    |  <------------------  |                     |
|                  |    ส่งผลลัพธ์กลับ      |                     |
+------------------+                      +---------------------+
                                                     |
                                                     v
                                           +---------------------+
                                           |  ไฟล์ข้อมูลบนดิสก์    |
                                           |  (data files)        |
                                           +---------------------+
```

- **Client** คือโปรแกรมที่ผู้ใช้หรือแอปพลิเคชันใช้ในการเชื่อมต่อและส่งคำสั่ง SQL ไปยังฐานข้อมูล เช่น `psql` (command-line tool อย่างเป็นทางการของ PostgreSQL), pgAdmin (โปรแกรม GUI), หรือแม้แต่โค้ดในแอปพลิเคชันที่เชื่อมต่อผ่าน driver/library ต่าง ๆ (เช่น `psycopg2` สำหรับ Python, `node-postgres` สำหรับ Node.js)
- **Server** คือตัว PostgreSQL เองที่รันอยู่บนเครื่อง (อาจเป็นเครื่อง local หรือเซิร์ฟเวอร์ระยะไกล/cloud) ทำหน้าที่รับคำสั่ง SQL มาประมวลผล จัดการข้อมูลบนดิสก์ และส่งผลลัพธ์กลับไปให้ client

Client และ Server สื่อสารกันผ่านเครือข่าย (แม้จะอยู่บนเครื่องเดียวกันก็ยังสื่อสารผ่าน protocol เดียวกัน) โดยใช้ **PostgreSQL wire protocol** ซึ่งเป็นโปรโตคอลเฉพาะของ PostgreSQL

### ภาพรวมของ Process Model (แบบเบื้องต้น)

เมื่อคุณเชื่อมต่อไปยัง PostgreSQL server สิ่งที่เกิดขึ้นเบื้องหลังคร่าว ๆ มีดังนี้:

1. มี process หลักที่เรียกว่า **postmaster** ทำหน้าที่คอยรับการเชื่อมต่อใหม่ที่เข้ามา
2. เมื่อมี client เชื่อมต่อเข้ามาใหม่ postmaster จะสร้าง **backend process** แยกต่างหากขึ้นมาหนึ่งตัวเพื่อรับผิดชอบ connection นั้นโดยเฉพาะ (นี่คือ process-based model ซึ่งต่างจากบางระบบที่ใช้ thread-based model)
3. Backend process นี้จะทำหน้าที่แปลคำสั่ง SQL, วางแผนการทำงาน (query planning), ดำเนินการค้นหา/แก้ไขข้อมูล และส่งผลลัพธ์กลับไปยัง client
4. นอกจากนี้ยังมี **background process** อื่น ๆ ที่ทำงานอยู่เบื้องหลังตลอดเวลา เช่น process ที่คอยเขียน log การเปลี่ยนแปลงข้อมูล (WAL writer), process ที่คอยทำความสะอาดพื้นที่ที่ไม่ใช้แล้ว (autovacuum), process ที่คอยเขียนข้อมูลจาก memory ลงดิสก์ (background writer)

```
                    postmaster (process หลัก)
                          |
        +-----------------+-----------------+
        |                 |                 |
   backend process    backend process    background
   (สำหรับ client A)   (สำหรับ client B)   processes
                                          (WAL writer,
                                           autovacuum,
                                           checkpointer ฯลฯ)
```

จุดที่น่าสนใจคือ **แต่ละ connection จะได้ backend process ของตัวเอง** ทำให้แต่ละการเชื่อมต่อทำงานแยกจากกันอย่างชัดเจน (isolation ในระดับ process) นี่คือเหตุผลหนึ่งที่ทำให้เมื่อมีการเชื่อมต่อจำนวนมาก ๆ พร้อมกัน มักมีการใช้เครื่องมือช่วยจัดการ เช่น connection pooler เพื่อจัดการทรัพยากรอย่างมีประสิทธิภาพ — เรื่องนี้เราจะพูดถึงอย่างละเอียดในบทที่ว่าด้วยการจูนประสิทธิภาพขั้นสูงของหลักสูตร

### เก็บข้อมูลอย่างไร (ภาพรวม)

ข้อมูลของ PostgreSQL ถูกจัดเก็บในรูปแบบไฟล์บนดิสก์ภายในโครงสร้างไดเรกทอรีที่เรียกว่า **data directory** โดยข้อมูลแต่ละตารางจะถูกแบ่งเก็บเป็นไฟล์ (และอาจแบ่งเป็นหลายไฟล์เมื่อขนาดใหญ่ขึ้น) พร้อมกับมีกลไกสำคัญที่เรียกว่า **WAL (Write-Ahead Log)** ที่คอยบันทึกทุกการเปลี่ยนแปลงก่อนที่จะเขียนลงไฟล์ข้อมูลจริง เพื่อรับประกัน Durability ตามหลักการ ACID ที่เราพูดถึงไปแล้วใน Step 4

นี่เป็นเพียงภาพรวมแบบกว้าง ๆ ให้คุณได้เห็นโครงร่างคร่าว ๆ ก่อน ในบทที่ว่าด้วย "สถาปัตยกรรมภายในของ PostgreSQL" ในระดับที่ลึกขึ้นของหลักสูตรนี้ เราจะผ่าให้เห็นรายละเอียดของแต่ละองค์ประกอบอย่างครบถ้วน รวมถึง MVCC (Multi-Version Concurrency Control) ซึ่งเป็นกลไกสำคัญที่ทำให้ PostgreSQL จัดการเรื่อง concurrency และ isolation ได้อย่างมีประสิทธิภาพ

## Step 9: ใครใช้ PostgreSQL บ้าง และเหมาะกับ Use Case แบบไหน

### องค์กรและผลิตภัณฑ์ที่ใช้ PostgreSQL

PostgreSQL ไม่ใช่ฐานข้อมูลสำหรับโปรเจกต์เล็ก ๆ เท่านั้น แต่ถูกใช้งานจริงในระบบระดับโลกจำนวนมาก ตัวอย่างที่เป็นที่รู้จักกันอย่างกว้างขวาง ได้แก่:

- **Instagram** ใช้ PostgreSQL เป็นฐานข้อมูลหลักในการเก็บข้อมูลผู้ใช้และโพสต์จำนวนมหาศาล
- **Spotify** ใช้ PostgreSQL ในหลายส่วนของระบบหลังบ้าน
- **Apple** ใช้ PostgreSQL อย่างกว้างขวางในหลายผลิตภัณฑ์และบริการภายใน
- **Reddit** ใช้ PostgreSQL เป็นส่วนสำคัญของโครงสร้างข้อมูล
- **Skype** (ในยุคแรก) เลือกใช้ PostgreSQL เพื่อรองรับระบบสื่อสารขนาดใหญ่
- ผู้ให้บริการ cloud รายใหญ่ทุกเจ้า ทั้ง **AWS** (Amazon RDS/Aurora for PostgreSQL), **Google Cloud** (Cloud SQL for PostgreSQL), และ **Microsoft Azure** (Azure Database for PostgreSQL) ต่างมีบริการ PostgreSQL แบบ managed service ของตัวเอง ซึ่งสะท้อนให้เห็นถึงความต้องการของตลาดที่สูงมาก
- สตาร์ทอัพและบริษัทเทคโนโลยีจำนวนมหาศาลทั่วโลกเลือก PostgreSQL เป็นฐานข้อมูลหลักตั้งแต่วันแรกของการสร้างผลิตภัณฑ์

นอกจากนี้ยังมีผลิตภัณฑ์ฐานข้อมูลเชิงพาณิชย์จำนวนมากที่สร้างขึ้นโดยใช้ PostgreSQL เป็นแกนหลัก (fork หรือ build on top of PostgreSQL) เช่น Amazon Redshift (data warehouse), CockroachDB (บางส่วนของ compatibility layer), Supabase (backend-as-a-service ยอดนิยม), Timescale Cloud และอีกมากมาย ซึ่งเป็นเครื่องพิสูจน์ถึงความแข็งแกร่งของสถาปัตยกรรมพื้นฐานของ PostgreSQL ที่สามารถนำไปต่อยอดได้หลากหลาย

### Use Case ที่ PostgreSQL เหมาะสมเป็นพิเศษ

- **ระบบธุรกิจทั่วไป (business applications)**: ระบบ ERP, CRM, ระบบจัดการคลังสินค้า ระบบจองต่าง ๆ ที่ต้องการความถูกต้องของข้อมูลและความสัมพันธ์ที่ซับซ้อน
- **ระบบการเงินและธนาคาร**: ที่ต้องการ ACID compliance อย่างเข้มงวด
- **แอปพลิเคชันเว็บและมือถือสมัยใหม่ (SaaS)**: ที่ต้องการความยืดหยุ่นของ JSON ผสมกับความถูกต้องของโครงสร้างเชิงสัมพันธ์
- **ระบบที่ต้องการข้อมูลภูมิสารสนเทศ (GIS)**: ผ่าน extension อย่าง PostGIS ซึ่งเป็นหนึ่งในระบบ GIS แบบโอเพนซอร์สที่ทรงพลังที่สุด
- **ระบบวิเคราะห์ข้อมูล (analytics) ขนาดกลางถึงใหญ่**: ด้วยความสามารถของ query ที่ซับซ้อนอย่าง window function, CTE (Common Table Expression), การรองรับ parallel query
- **ระบบที่ต้องการทำงานร่วมกับ AI/Machine Learning**: ด้วย extension อย่าง pgvector ที่รองรับการเก็บและค้นหา vector embedding ซึ่งเป็นหัวใจสำคัญของแอปพลิเคชัน AI สมัยใหม่ เช่น ระบบ RAG (Retrieval-Augmented Generation)
- **Time-series data**: ผ่าน extension อย่าง TimescaleDB สำหรับข้อมูลที่เปลี่ยนแปลงตามเวลา เช่น ข้อมูล IoT, ข้อมูล monitoring

### เมื่อไหร่ที่อาจต้องพิจารณาทางเลือกอื่น

เพื่อความเป็นธรรมและภาพที่สมดุล ควรกล่าวไว้ด้วยว่า PostgreSQL อาจไม่ใช่คำตอบที่เหมาะที่สุดในทุกสถานการณ์ เช่น:

- งานที่ต้องการ throughput การเขียนข้อมูลสูงมากในระดับกระจายทั่วโลกแบบ NoSQL บางประเภท อาจพิจารณาระบบที่ออกแบบมาเพื่อการกระจายข้อมูลระดับนั้นโดยเฉพาะ
- งาน caching ความเร็วสูงระดับ sub-millisecond อาจเหมาะกับ key-value store เฉพาะทางอย่าง Redis มากกว่า
- องค์กรที่ผูกติดกับระบบนิเวศเฉพาะทาง (เช่น ใช้ Microsoft stack ทั้งองค์กรอยู่แล้ว) อาจพบว่า SQL Server integrate ได้ราบรื่นกว่าในบริบทนั้น

อย่างไรก็ตาม สำหรับงานส่วนใหญ่ในโลกความเป็นจริง PostgreSQL คือตัวเลือกที่ **"ปลอดภัยและครบเครื่องที่สุด"** เพราะสามารถรองรับได้ทั้งงาน transactional แบบดั้งเดิม งาน analytics งาน JSON/document-style และงาน AI สมัยใหม่ได้ในระบบเดียว นี่คือเหตุผลที่หลักสูตรนี้เลือก PostgreSQL เป็นฐานข้อมูลหลักในการสอนตั้งแต่ต้นจนจบ

## Step 10: ภาพรวมหลักสูตรทั้งหมด — Roadmap การเรียนรู้

ตอนนี้คุณได้ปูพื้นฐานความคิดที่จำเป็นครบถ้วนแล้ว มาดูกันว่าตลอดหลักสูตรนี้คุณจะได้เดินทางผ่านอะไรบ้าง ตั้งแต่ระดับเริ่มต้นจนถึงระดับผู้เชี่ยวชาญระดับโลก

### ระดับที่ 1: พื้นฐาน (Foundations)

เริ่มจากบทนี้ที่ปูแนวคิดพื้นฐาน จากนั้นจะเรียนรู้การติดตั้ง PostgreSQL บนระบบปฏิบัติการต่าง ๆ การใช้เครื่องมือพื้นฐานอย่าง `psql`, การสร้างฐานข้อมูลและตารางแรกของคุณ, คำสั่ง SQL พื้นฐานสำหรับ CRUD (Create, Read, Update, Delete), data type ต่าง ๆ ของ PostgreSQL, และการออกแบบฐานข้อมูลเบื้องต้น

### ระดับที่ 2: SQL ขั้นกลาง (Intermediate SQL)

เจาะลึกการเขียน query ที่ซับซ้อนขึ้น เช่น การ `JOIN` ตารางหลายตาราง, การจัดกลุ่มและสรุปผลข้อมูล (`GROUP BY`, aggregate function), subquery, การจัดการ constraint และ index เบื้องต้น, transaction และการควบคุม concurrency ในทางปฏิบัติ

### ระดับที่ 3: การออกแบบฐานข้อมูล (Database Design)

หลักการ normalization อย่างละเอียด (1NF ถึง BCNF และไกลกว่านั้น), การออกแบบ schema ที่ดี, การสร้างแบบจำลองข้อมูล (ER diagram), การตัดสินใจเรื่อง normalize vs denormalize ในสถานการณ์จริง

### ระดับที่ 4: SQL ขั้นสูง (Advanced SQL)

Window function, Common Table Expression (CTE) แบบ recursive, การเขียน query ที่ซับซ้อนระดับ analytics, full-text search, การทำงานกับ JSON/JSONB อย่างลึกซึ้ง, array และ custom data type

### ระดับที่ 5: สถาปัตยกรรมภายในของ PostgreSQL

MVCC (Multi-Version Concurrency Control) แบบละเอียด, WAL (Write-Ahead Logging), process model แบบเต็มรูปแบบ, memory architecture (shared buffers, work_mem และอื่น ๆ), storage layer และวิธีที่ PostgreSQL จัดเก็บข้อมูลบนดิสก์จริง ๆ

### ระดับที่ 6: ประสิทธิภาพและการจูนระบบ (Performance & Tuning)

การอ่านและตีความ `EXPLAIN`/`EXPLAIN ANALYZE`, การออกแบบ index อย่างมีประสิทธิภาพ (B-tree, GIN, GiST, BRIN และอื่น ๆ), query optimization, การจูน configuration parameter, connection pooling, partitioning สำหรับตารางขนาดใหญ่

### ระดับที่ 7: การดูแลระบบ (Administration & Operations)

การจัดการ user และสิทธิ์การเข้าถึง, backup และ recovery (รวมถึง point-in-time recovery), replication (streaming replication, logical replication), high availability, monitoring และการวางแผนความจุ (capacity planning)

### ระดับที่ 8: ความปลอดภัย (Security)

authentication และ authorization ขั้นสูง, row-level security, การเข้ารหัสข้อมูล, การป้องกัน SQL injection และภัยคุกคามอื่น ๆ, auditing

### ระดับที่ 9: หัวข้อขั้นสูงและระบบนิเวศ (Advanced Topics & Ecosystem)

Extension สำคัญ เช่น PostGIS (GIS), pgvector (AI/vector search), TimescaleDB (time-series), การทำงานร่วมกับภาษาโปรแกรมมิ่งต่าง ๆ ผ่าน driver/ORM, PostgreSQL บน cloud (managed services), การย้ายระบบจากฐานข้อมูลอื่นมา PostgreSQL

### ระดับที่ 10: ระดับผู้เชี่ยวชาญระดับโลก (World-Class Expert)

การมีส่วนร่วมกับ PostgreSQL community, การอ่านและทำความเข้าใจ source code บางส่วน, การแก้ปัญหาระบบระดับ production ที่ซับซ้อนที่สุด, best practice จากประสบการณ์จริงในองค์กรระดับโลก, และแนวโน้มอนาคตของ PostgreSQL

```
พื้นฐาน → SQL ขั้นกลาง → การออกแบบฐานข้อมูล → SQL ขั้นสูง
   → สถาปัตยกรรมภายใน → ประสิทธิภาพและการจูนระบบ
   → การดูแลระบบ → ความปลอดภัย → หัวข้อขั้นสูง/ระบบนิเวศ
   → ระดับผู้เชี่ยวชาญระดับโลก
```

แต่ละระดับจะถูกแบ่งย่อยเป็น "Part" ต่าง ๆ (เช่นเดียวกับ Part 001 นี้) ซึ่งแต่ละ Part จะมี 10 Step ที่ค่อย ๆ พาคุณเดินไปทีละก้าวอย่างมั่นคง ไม่กระโดดข้ามความรู้พื้นฐานใด ๆ ไป ทุกแนวคิดจะถูกอธิบายพร้อมเหตุผล ตัวอย่างจริง และแบบฝึกหัดเพื่อให้คุณได้ลงมือปฏิบัติจริง

## สรุปท้ายบท

ในบทนี้เราได้ปูพื้นฐานความคิดที่สำคัญที่สุดก่อนเริ่มต้นเดินทางกับ PostgreSQL:

- **Database** คือระบบที่แก้ปัญหาที่ไฟล์ธรรมดาหรือ Excel ทำไม่ได้ดี ทั้งเรื่องข้อมูลซ้ำซ้อน การเข้าถึงพร้อมกัน ความถูกต้องของข้อมูล และการขยายขนาด
- ฐานข้อมูลแบ่งได้เป็นหลายตระกูล ได้แก่ **Relational (RDBMS)**, **NoSQL**, และ **NewSQL** โดยแต่ละแบบเหมาะกับสถานการณ์ต่างกัน
- **RDBMS** เก็บข้อมูลเป็น **table** ที่มี **row** และ **column** และเชื่อมโยงตารางต่าง ๆ ด้วยความสัมพันธ์ผ่าน primary key และ foreign key
- หลักการ **ACID** (Atomicity, Consistency, Isolation, Durability) คือรากฐานที่ทำให้ RDBMS อย่าง PostgreSQL น่าเชื่อถือสำหรับงานที่ต้องการความถูกต้องสูง เช่น ระบบการเงิน
- **SQL** คือภาษามาตรฐานสำหรับสื่อสารกับ RDBMS แบ่งเป็น 5 กลุ่มคำสั่งหลัก: DDL, DML, DQL, DCL, TCL
- **PostgreSQL** มีประวัติยาวนานกว่า 40 ปี ตั้งแต่ยุค Ingres ที่ Berkeley จนถึงปัจจุบัน เป็นฐานข้อมูลโอเพนซอร์สที่ได้รับการยกย่องว่า "advanced" ที่สุดตัวหนึ่งของโลก
- PostgreSQL มีจุดเด่นหลายด้านเมื่อเทียบกับ MySQL, SQL Server, Oracle และ MongoDB โดยเฉพาะเรื่องความยึดมั่นต่อมาตรฐาน SQL, ความสามารถขั้นสูง, extensibility และการเป็นโอเพนซอร์สอย่างแท้จริง
- สถาปัตยกรรมพื้นฐานของ PostgreSQL เป็นแบบ **client-server** โดยแต่ละ connection จะมี backend process ของตัวเอง และมีกลไก WAL คอยรับประกัน Durability
- องค์กรระดับโลกจำนวนมาก ตั้งแต่ Instagram, Spotify, Apple ไปจนถึงผู้ให้บริการ cloud รายใหญ่ ต่างใช้และสนับสนุน PostgreSQL
- หลักสูตรนี้จะพาคุณเดินทางจากพื้นฐานไปจนถึงระดับผู้เชี่ยวชาญระดับโลก ผ่าน 10 ระดับความรู้ที่ค่อย ๆ ยกระดับความซับซ้อนขึ้นทีละขั้น

ในบทถัดไป เราจะเริ่มลงมือจริงด้วยการติดตั้ง PostgreSQL บนเครื่องของคุณ และทำความรู้จักเครื่องมือพื้นฐานที่จะใช้ตลอดหลักสูตรนี้

## แบบฝึกหัด

ลองตอบคำถามต่อไปนี้ด้วยความเข้าใจของตัวเอง (ไม่ต้องท่องจำ) แล้วตรวจคำตอบกับเฉลยท้ายบท

**1.** อธิบายปัญหาอย่างน้อย 3 ข้อที่เกิดขึ้นเมื่อองค์กรเก็บข้อมูลลูกค้าด้วยไฟล์ Excel แทนที่จะใช้ database ที่เหมาะสม

**2.** ฐานข้อมูลประเภท Relational, NoSQL และ NewSQL แตกต่างกันอย่างไร ยกตัวอย่างสถานการณ์ที่แต่ละประเภทเหมาะสมที่สุด

**3.** ในตาราง `orders` ที่มีคอลัมน์ `customer_id` เชื่อมโยงไปยังตาราง `customers` คอลัมน์ `customer_id` นี้เรียกว่าอะไร และทำหน้าที่อะไร

**4.** อธิบายหลักการ ACID แต่ละข้อโดยใช้ตัวอย่างระบบ "จองตั๋วภาพยนตร์" (ไม่ใช่ตัวอย่างโอนเงินที่ใช้ในบทเรียน) — ลองคิดว่าถ้าขาดหลักการแต่ละข้อไป จะเกิดปัญหาอะไรกับระบบจองตั๋ว

**5.** คำสั่ง SQL ต่อไปนี้จัดอยู่ในกลุ่มใด (DDL, DML, DQL, DCL, หรือ TCL): `CREATE TABLE`, `SELECT`, `GRANT`, `UPDATE`, `ROLLBACK`

**6.** PostgreSQL มีต้นกำเนิดมาจากโครงการชื่ออะไรที่มหาวิทยาลัย Berkeley และใครคือผู้ก่อตั้งโครงการนี้

**7.** ยกตัวอย่างจุดเด่น 3 ข้อของ PostgreSQL เมื่อเทียบกับฐานข้อมูลเชิงพาณิชย์อย่าง Oracle Database หรือ SQL Server

**8.** ในสถาปัตยกรรมแบบ client-server ของ PostgreSQL เมื่อมี client เชื่อมต่อเข้ามาใหม่ จะเกิดอะไรขึ้นกับ process ฝั่ง server

**9.** ยกตัวอย่าง use case อย่างน้อย 2 ประเภทที่ PostgreSQL เหมาะสมเป็นพิเศษ พร้อมอธิบายเหตุผลสั้น ๆ ว่าทำไมถึงเหมาะ

**10.** ทำไมการเข้าใจแนวคิดพื้นฐานในบทนี้ (ก่อนเริ่มเขียน SQL จริง) จึงมีความสำคัญต่อการเรียนรู้ในบทถัดไปของหลักสูตร

## เฉลย

**1.** ตัวอย่างปัญหาที่เกิดขึ้น (ตอบได้หลายข้อ เช่น): ข้อมูลซ้ำซ้อนเมื่อลูกค้าคนเดิมมีหลายรายการ ทำให้แก้ไขข้อมูลยากและเสี่ยงข้อมูลไม่ตรงกัน; ไม่มีการควบคุมเมื่อหลายคนแก้ไขไฟล์พร้อมกัน ทำให้ข้อมูลถูกเขียนทับหายไป; ไม่มีการตรวจสอบความถูกต้องของข้อมูล ทำให้กรอกข้อมูลผิดรูปแบบได้ง่าย; ประสิทธิภาพตกลงเมื่อข้อมูลมีขนาดใหญ่; ไม่มีระบบสำรองและกู้คืนข้อมูลที่น่าเชื่อถือ; ความปลอดภัยต่ำ ควบคุมสิทธิ์การเข้าถึงได้จำกัด

**2.** **Relational** เก็บข้อมูลเป็นตารางที่มี schema ชัดเจน เน้น ACID เหมาะกับข้อมูลที่มีความสัมพันธ์ซับซ้อน เช่น ระบบธนาคาร **NoSQL** ยืดหยุ่นเรื่องโครงสร้างข้อมูล เหมาะกับข้อมูลที่เปลี่ยนแปลงบ่อยหรือไม่แน่นอน เช่น content management ที่แต่ละบทความมีฟิลด์ไม่เหมือนกัน หรือระบบ caching ที่ต้องการความเร็วสูงสุด **NewSQL** ผสมผสาน ACID + SQL เข้ากับความสามารถในการขยายระบบขนาดใหญ่ เหมาะกับระบบระดับโลกที่ต้องการทั้งความถูกต้องและปริมาณข้อมูลมหาศาลกระจายหลายภูมิภาค

**3.** คอลัมน์ `customer_id` เรียกว่า **foreign key** ทำหน้าที่อ้างอิงกลับไปยัง primary key (`id`) ของตาราง `customers` เพื่อเชื่อมโยงว่าคำสั่งซื้อแต่ละรายการเป็นของลูกค้าคนใด โดยไม่ต้องเก็บข้อมูลลูกค้าซ้ำในตาราง `orders`

**4.** ตัวอย่างคำตอบ (ระบบจองตั๋วภาพยนตร์):
- **Atomicity**: การจองตั๋วประกอบด้วยการเลือกที่นั่งและการตัดเงิน หากขาด atomicity อาจเกิดกรณีที่นั่งถูกจองแล้วแต่เงินไม่ถูกตัด หรือเงินถูกตัดแต่ที่นั่งไม่ถูกจอง
- **Consistency**: ต้องรับประกันว่าที่นั่งหนึ่งที่จะถูกขายให้คนเดียวเท่านั้น หากขาด consistency อาจมีที่นั่งเดียวกันถูกขายซ้ำให้สองคน
- **Isolation**: หากสองคนพยายามจองที่นั่งเดียวกันพร้อมกัน ระบบต้องจัดการให้คนใดคนหนึ่งจองสำเร็จเพียงคนเดียว หากขาด isolation ทั้งสองคนอาจเห็นว่าที่นั่งว่างพร้อมกันและจองซ้ำกันได้
- **Durability**: เมื่อจองสำเร็จและระบบแจ้งว่า "จองแล้ว" ข้อมูลนั้นต้องไม่หายไปแม้ระบบจะล่มทันทีหลังจากนั้น หากขาด durability ลูกค้าอาจเสียเงินไปแล้วแต่ไม่มีที่นั่งจริง

**5.** `CREATE TABLE` = DDL, `SELECT` = DQL, `GRANT` = DCL, `UPDATE` = DML, `ROLLBACK` = TCL

**6.** PostgreSQL มีต้นกำเนิดจากโครงการ **Ingres** และต่อมาคือ **Postgres** ที่มหาวิทยาลัย **University of California, Berkeley** โดยมี **Michael Stonebraker** เป็นผู้ก่อตั้งและผู้นำโครงการหลัก

**7.** ตัวอย่างคำตอบ (เลือกตอบ 3 ข้อจากที่มีในบทเรียน): เป็นโอเพนซอร์สและฟรีอย่างแท้จริง ไม่มีค่าใช้จ่าย license; ยึดมั่นในมาตรฐาน SQL อย่างเคร่งครัดมากกว่าหลายผลิตภัณฑ์; มี extensibility สูง สามารถเพิ่ม extension เช่น PostGIS, pgvector ได้; พัฒนาโดยชุมชนที่เป็นกลาง ไม่ผูกกับบริษัทใดบริษัทหนึ่งเหมือน Oracle หรือ Microsoft

**8.** เมื่อมี client เชื่อมต่อเข้ามาใหม่ process หลักที่เรียกว่า **postmaster** จะสร้าง **backend process** ใหม่ขึ้นมาหนึ่งตัวโดยเฉพาะสำหรับ connection นั้น ทำให้แต่ละ connection ทำงานแยกจากกันในระดับ process

**9.** ตัวอย่างคำตอบ: (1) ระบบการเงิน/ธนาคาร เพราะต้องการความถูกต้องของข้อมูลระดับ ACID สูงสุด; (2) ระบบที่ต้องการข้อมูลภูมิสารสนเทศ (GIS) เพราะมี extension PostGIS ที่ทรงพลัง; (3) แอปพลิเคชัน AI สมัยใหม่ที่ต้องการเก็บและค้นหา vector embedding เพราะมี extension pgvector; (4) ระบบ SaaS ที่ต้องการทั้งความยืดหยุ่นของ JSON และความถูกต้องเชิงสัมพันธ์ในระบบเดียว

**10.** เพราะคำสั่ง SQL ทุกคำสั่งที่จะได้เรียนต่อจากนี้ล้วนสร้างอยู่บนแนวคิดพื้นฐานเหล่านี้ทั้งสิ้น เช่น การเข้าใจว่า table/row/column ทำงานอย่างไรจะช่วยให้เข้าใจคำสั่ง `CREATE TABLE` ได้ทันที การเข้าใจ ACID จะช่วยให้เข้าใจว่าทำไมต้องมีคำสั่ง `COMMIT`/`ROLLBACK` การเข้าใจความสัมพันธ์ระหว่างตารางจะช่วยให้เข้าใจคำสั่ง `JOIN` ได้อย่างเป็นธรรมชาติ กล่าวคือ **เมื่อเข้าใจ "ทำไม" ก่อน การเรียนรู้ "อย่างไร" จะง่ายและจำได้แม่นยำกว่ามาก**
